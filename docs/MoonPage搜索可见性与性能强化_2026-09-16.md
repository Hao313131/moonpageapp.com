### 3.1 GSC 验证 —— 已完成（原计划的 meta 标签路线作废）

**2026-09-16 你在 Search Console 里看到「您是经过验证的所有者」→ 资源已验证。**

**所以下面这条路不用走了**：`GSC_VERIFICATION` secret → `NEXT_PUBLIC_GSC_VERIFICATION` → `<meta name="google-site-verification">`。
我实测过线上首页，**一个搜索引擎验证标签都没有**（`google-site-verification` / `msvalidate.01` / `yandex-verification` / `p:domain_verify` 全为 0），

### 3.2 Cloudflare 前置 —— 需要你的 Cloudflare 账号 + 域名 NS

**为什么我做不到**：需要你的 Cloudflare 账号（我没有 CF API token），
且**必须到域名注册商处把 nameserver 改成 Cloudflare 分配的 NS** —— 这一步只有域名所有者能做。

**为什么值得做**：一次同时解决四件事 —— 缓存头（GitHub Pages 无视 `_headers`）、legacy slug 301、https 强制、Brotli + HTTP/3。
这也是 LCP 剩余最大的杠杆。

**你要做**：

| 步骤 | 操作 |
|---|---|
| 1 | 注册 Cloudflare → 添加站点 `moonpageapp.com` |
| 2 | 到注册商处把 NS 改为 Cloudflare 分配的地址 |
| 3 | DNS：apex A → GitHub 的 4 个 IP（橙云）；<br>`www` CNAME → `hao313131.github.io`（橙云） |
| 4 | SSL/TLS → 模式 **Full (strict)**；<br>开 Always Use HTTPS、HTTP/3、Brotli |
| 5 | Caching → Cache Rules：复刻 `public/_headers` 的 3 组规则 |
| 6 | Rules → Redirect Rules：复刻 `public/_redirects` 的 www 与 legacy slug 301 |

规则来源就是仓库里的两个文件（Cloudflare 规则照它们复刻即可）：
`public/_headers`（缓存头）、`public/_redirects`（www 与 legacy slug 的 301）。
这两个文件在 GitHub Pages 上**完全无效**（实测图片缓存 `max-age=600`、legacy slug 404），
所以内容本身是对的，只是需要一个能读它们的 CDN 前置。

### 3.4 顺带修掉的三个隐患

| 隐患 | 原来 | 现在 |
|---|---|---|
| **站点级评价无法提交** | `__site__` 这个 key **没有任何表单能产生**，<br>首页评分永远拿不到数据 | 首页新增站点级评价区（`/` 页） |
| **标记与可见区脱钩** | `MobileApplication.aggregateRating` 写在全局 layout，<br>会出现在**每一页**，但可见评价只在某一页 | 评分改为**只在首页**通过 `@id` 合并进同一实体，<br>**标记 ⟺ 可见**严格成立 |
| **激活后可能「永久报错」** | 响应判定是**精确匹配字符串 `"true"`**。<br>而我们只实测到过**拒绝**形状（`"false"`），<br>**接受**形状在激活前无法触发。<br>若真实返回是布尔 `true` 而非字符串，<br>则**每一次真实提交都会显示报错**——<br>恰好是这个表单最不能出的故障 | 判定改为**容错**：布尔 / 数字 / 常见 yes-no 字符串统一归一；<br>依次读 `success` → `ok` → `status`；<br>正文没有明确表态时**信 HTTP 2xx**，<br>除非含已实测到的拒绝用语（activation / captcha / blacklist 等）。<br>邮件兜底仍覆盖所有判为失败的分支 →<br>**改动只可能消掉误报，不可能弄丢评价** |

> 第 3 条是本轮最后一块拼图。搜索 GitHub 上 17,984 个用到 FormSubmit 的仓库想找「成功响应长什么样」，
> 结论是**找不到**——抽样的仓库全部只判断 `res.ok`、从不看响应体（4 个样本是同一份教程的复制粘贴）。
> 既然外部证据拿不到，就**不把正确性押在一个无法验证的细节上**，改成容错实现。

| 修改 | `package.json` | 新增 `gen:legacy-redirects`，<br>并**追加到 `build` 的最后一环** |
| 修改 | `app/stories/page.tsx` | `/stories/` 描述重写（148 → **155** 字符） |

**为什么这一步必须放在 `validate:seo` 之后**：闸门要求**每一页 canonical 指向自己**，
而重定向桩**合法地**把 canonical 指向别处。桩不是内容页、不进 sitemap，
所以它**不在闸门管辖范围内** —— 管住它的是脚本里的「目标必须存在于同一次构建」硬校验。

**为什么不是 301**：GitHub Pages 上 `public/_redirects` **完全无效**（实测 legacy slug 仍 404），
而 Next.js 在 `output:"export"` 下不产出 redirect。canonical + 零秒 meta refresh 是**这个主机上仅剩的、Google 明确承认的**重定向信号。

**为什么桩上故意不加 `noindex`**：`noindex` 会让 Google **直接丢弃**这个 URL 而不做合并，
与重定向的目的**正好相反**，而且两者互相矛盾。

**对同一个 slug 指向了不同目标**。这个分歧今天不产生任何影响（GitHub Pages 完全无视 `_redirects`），

现在改为**单一来源**：legacy 规则由 `scripts/gen-legacy-redirects.mjs` 从 JSON 生成、追加进 `out/_redirects`，

**实现上还有一条硬约束**：`scripts/gen-legacy-redirects.mjs` 只在**目标存在于同一次构建**时才写桩，否则直接构建失败 ——
所以不可能出现「重定向进 404」。
